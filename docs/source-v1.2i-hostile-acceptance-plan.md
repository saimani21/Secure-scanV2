### I-B expired-scanner recovery defect fix (2026-10-01)

- **Root cause:** `SourceScannerLeaseReconciliationService.quarantine_expired` moved expired `ACTIVE` attempts to `RECONCILIATION_REQUIRED` but never advanced an attempt with verified clean containment. Generic lease recovery deliberately excludes scanner jobs. The disposable M2 observation therefore remained `RUNNING` and unpublished after worker death; it did not produce false-clean evidence.
- **Fix:** `src/securescan/orchestration/execution.py` now reconciles only the exact expired, current, pending attempt. A local scanner retry requires its exact attempt-bound, stable cleanup receipt and a fresh process-tree absence check; Semgrep requires the existing Docker sandbox reconciler's removal proof. A missing, contradictory or unverifiable receipt quarantines without retry. Under one parent-ordered database transaction, verified clean recovery records a failed `ToolExecution`, rejects/fences the old attempt and lease token, and moves the existing job/node to bounded `RETRY_PENDING` or a terminal state when cancelled, expired or out of attempts. `src/securescan/source_runtime.py` wires the private local receipt root and existing Semgrep reconciler into the production runtime. No scanner result, S4, Product Core or governance semantics changed.
- **New proof:** `tests/test_hostile_worker_recovery_diagnosis_v12i.py` now has nine passing cases covering unknown, clean, missing and contradictory local receipts; clean and unknown Semgrep cleanup; stale original submission both before and after retry acceptance; exactly one accepted retry result; exhausted budget; and cancellation. `tests/test_postgres_source_orchestration_s6b.py` adds two real PostgreSQL races: two recovery cycles produce one rejected attempt/retry winner, and cancellation racing recovery cannot release a new attempt. The complete PostgreSQL orchestration file passed 9/9.
